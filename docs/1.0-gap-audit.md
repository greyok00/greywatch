# The road to GreyWatch 1.0

Audit written 2026-11-07 against master commit 01165c8 (suite pinned at
that commit). It answers one question: what stands between the current
0.2.x line and a defensible 1.0 "stable" tag, and which parts of that
gap are work the owner can commission locally versus facts the owner
must supply (grants, service restart, final approval).

## Where the program stands

The rebuild gameplan (`~/Desktop/greywatch-rebuild-gameplan.txt`) ran
its phases to completion: the four-page shell, the one decision list,
the theme system, the shipped-text sweep, the 0.2.0 recut, then the
post-release lines - the patch-the-planet watchlist, the unconfuse
wave, the human-style visual audit (walkthrough manual + PDF), and the
cannot-fail sweep with four doctor lanes and machine-readable health
(`docs/cannot-fail-map.md`). Every one of those waves ended suite
green. What the suite green count does not prove is written below.

## Owner-supplied gaps (not code)

These are the only items that make "complete" impossible from this
machine alone. They are listed first because they gate the last step
of every line of work below.

1. **Two push grants.** Twenty commits (watchlist line through the
   cannot-fail sweep) sit unpushed on master; v0.2.0 tag moved to
   01165c8 locally. No release exists publicly at 0.2.x. 1.0 needs a
   public history, so these grants are the wall.
2. **greywatch.service restart.** The running root daemon still
   executes pre-wave code. The evidence is on disk: the live
   events.jsonl holds 108,205 lines against a 20,000-line trim cap
   that the current tree enforces hourly. Until the service restarts,
   new status.json keys and the doctor lane stay unproven live.
3. **Final approval.** The program's own closing gate, plus the owner
   confirmations listed in Amendments D and Part 8 (auto-lift live
   exercise witnessed, fresh-sweep after arming).

## Code gaps this line can close (0.3.0 waves)

Each wave ends with the full suite green and a commit. Twins gate and
the em-dash rule apply to every wave.

- **Wave F1: Phase 4 leftover.** The gameplan's Phase 4 target is
  window.py under ~1500 lines; it stands at 1755. Extract the tool
  lifecycle + detail block (pause/resume/reconcile, control and
  state plumbing, detail card) into a `ui/toolctl.py` mixin in the
  established LogsDeskMixin style, and lift `ProgressCircle`/`_theme_g`
  to the metrics module. Done when: window.py < 1500 lines and the
  suite pins that still reference window.py stay green without edits
  beyond re-rooting.
- **Wave F2: data hygiene for stability.** 1.0 must not grow files
  without bound. trim_events reads the whole ledger into memory each
  hour; make it tail-based (seek), verify the cap path, and add caps
  or documented growth policy for learning-seen.jsonl and malformed
  log; the doctor's backlog row reports ledger sizes in one place.
  Done when: tests pin the trim on a file over cap and the doctor
  row names a grown ledger.
- **Wave F3: 1.0 documentation set.** No CHANGELOG exists, the README
  test badge says 1665 passing (stale), and there is no man page or
  upgrade note for 0.1.x installs moving to 0.3. Done when: CHANGELOG
  per line, README badge regenerated from the real count, man page
  for the CLI and doctor, an upgrade block in install.sh's output or
  README.
- **Wave F4: stability proof.** Doctor machine mode green on the
  sandbox dir, a timed soak of the daemon loop (N cycles, no growth,
  no unhandled failure), the release.yml workflow re-added if the
  0.3.0 tag ever gets push grants (it was dropped from the tree;
  v0.1.7 pinning lesson from the ABI memory says it must exist before
  any future public tag), and the packaging checklist executed with
  all three artifacts recut plus SHA256SUMS.
- **Wave F4a: test-harness livelock fix (found during the gate).**
  Under a heavily loaded box (Godot + llamacpp holding 18-24 load),
  the full suite stalled inside the GTK pump helpers: every
  `MainWindow` registers a 5s periodic refresh and a 1s scan tick, and
  one dispatch of either runs a full data-dir refresh plus the
  overview's decision-gate parse (a gdb native backtrace caught
  `_periodic_refresh > refresh > OverviewPage._paint_gate >
  decisions_factory.pending_spec_pairs` inside a stall). A pump that
  drains up to 500 dispatches per pass could therefore burn minutes
  on refresh chains that belong to timers, not to the assertion. The
  fix follows the tab_shell precedent ("silence the periodic tick,
  never mask the assertion"): the chooser test removes its window's
  timers before pumping, and every pump drain checks the clock per
  dispatch so one long refresh cannot exceed the pump's budget.
  Done when: the four affected suites pass standalone in seconds and
  the full gate completes inside its timeout window.
- **Wave F5: recut and local tag v0.3.0.** Version bump to 0.3.0,
  build-cython, wheel/deb/tarball, checksums, changelog cross-checked,
  tag moved locally. Push and gh release stay owner-grant blocks.

## What "1.0 stable" should mean here (definition of done for the line)

- The full suite green; no test carries an open skip reason the
  cannot-fail map has not explained.
- Two consecutive release lines (0.2.x, 0.3.x) shipped with the same
  packaging checklist and no post-ship defect fix in the data loss
  class (the flush-outbox counting bug was the last one of that kind).
- The daemon survives a live service restart with its data intact and
  the doctor says so in machine mode.
- Every ledger has a stated cap or growth policy, enforced by code
  and pinned by a test.
- The manual (walkthrough) and the cannot-fail map match the shipped
  behavior of the tagged commit.

The difference between 0.3.0 and 1.0 then becomes purely the
owner-supplied items above: a pushed history, the live restart proof,
and final approval. That is the honest gap; no unshipped feature work
is hiding behind it.
